Fixes

Findings #6 + #26 CliInvocation.Snapshot() full-copy per tick

Decision

New cursor-based incremental API: int OutputCursor (a monotonic append count) plus CopyNewLines(int fromCursor, ICollection<CliOutputLine>) returning the next cursor. Cursors are positions in the append sequence, not list indices, so trimming can never renumber a reader; a lagging reader instead gets an explicit notice of how many lines it missed. Snapshot() is kept — now one copy under one lock instead of three — but has zero production callers once all three consumers (upgrade console, Activity panel, wizard console) are migrated to CopyNewLines with reusable buffers.

Before
Every 250–500 ms UI tick copied the full accumulated transcript (twice, plus once per loop iteration in two of the consumers).
After
One lock plus only the lines that actually arrived; zero steady-state allocation.

Finding #14 Unbounded per-invocation output

Decision

Two caps: MaxRetainedOutputLines = 2,000 and MaxRetainedOutputBytes = 256 KiB per invocation — 256 KiB × the 200-entry Activity ring gives a 50 MiB hard ceiling on all retained CLI text. Trim drops oldest lines down to a 75% low-water mark in one RemoveRange call (once per quarter-budget, not per line); the newest line is never dropped. Truncation is surfaced honestly: a synthesized [output truncated] N earlier line(s) dropped… marker goes into a new third stream, CliStream.Notice — deliberately not stdout/stderr, since call sites parse those (LastOrDefault(stderr) for error messages; PluginsPanel parses concatenated stdout). Exit code, failure reason, argv, and duration are never trimmed. Required follow-up: ActivityPanelViewModel and WizardViewModel still did index-based delta reads that would silently skip ~500 lines per trim event — both were migrated to the cursor API; a grep confirms zero index-based readers remain.

Before
A single long-running invocation could accumulate output without limit.
After
Output is capped per invocation at 2,000 lines / 256 KiB, with an explicit truncation marker on a dedicated stream and no impact on stdout/stderr parsing.

Finding #7 Updates console scrolled once per line, non-virtualized

Decision

Mirrored the Logs panel's proven pattern rather than inventing one. (a) Coalesced scroll: a _scrollScheduled guard with Dispatcher.BeginInvoke(Background) gives one scroll per batch of appended lines instead of one per line. (b) Virtualization: the ItemsControl-in-ScrollViewer became a ListBox with IsVirtualizing + Recycling mode; the ItemContainerStyle strips ListBoxItem down to a bare ContentPresenter so the console still looks identical (non-interactive, no selection chrome). IsOutputPaused is re-checked both at schedule time and inside the deferred callback.

Before
Verbose resolver runs caused visible judder — a full layout pass per line against a fully-realized list.
After
One coalesced scroll per tick against a list that only realizes on-screen rows.

Finding #8 Logs filter re-projected 5,000 lines per keystroke

Decision

Delay=400 on the FilterText binding — the exact value and mechanism the Audit panel's identical filters already use (AuditPanel.xaml lines 162/169). WPF's binding delay defers the source update itself, so no new timer plumbing is needed. Consistency with the sibling panel was chosen over the verifier's alternate 300 ms.

Before
Every keystroke synchronously cleared and re-filled the displayed collection from the 5,000-line buffer.
After
Re-projection fires once typing pauses for 400 ms. Match semantics unchanged.

Finding #18 No global exception handlers

Decision

All three handlers — DispatcherUnhandledException, TaskScheduler.UnobservedTaskException, and AppDomain.UnhandledException — are wired as the first statements of OnStartup, before any service construction. Continue-vs-crash criterion: a _shellReady flag set as the last statement of startup. Dispatcher faults are swallowed (Handled=true) only after tray, window, and monitor are fully up, because before that point the tray isn't a usable control surface and swallowing would leave an invisible zombie process. On a handled fault: the window is hidden (never a live tray with a broken window), one honest dialog is shown, rate-limited to 1 per 30 s, and the full exception is logged. UnobservedTaskException calls SetObserved and logs, never fatal. AppDomain does a last-resort log, nothing swallowed. Crash log path: %LOCALAPPDATA%\DefenseClaw.App\logs\crash-<timestamp>-<pid>.log, keeping the newest 10 files, with a 1 MB per-session cap and explicit marker; every path is exception-proofed so the handler itself can never throw.

Before
Any dispatcher fault silently killed the process — the tray shield just vanished, no log, no dialog.
After
Faults after startup completes are caught, logged, and surfaced via a rate-limited dialog instead of killing the process silently.

Files

  • DefenseClaw.App/App.xaml.cs
Residual risk: handled dispatcher faults may leave view-model state inconsistent (mitigation: window hidden, reopen rebuilds); the MessageBox shown in the dispatcher handler pumps messages re-entrantly, bounded by the 30 s throttle.

Finding #20 Config-change event mutated UI collections off-thread

Decision

Marshal once at the App boundary: AppServices.RaiseConfigReloaded resolves Application.Current.Dispatcher at raise time (CheckAccess/BeginInvoke — the shell's dominant pattern). Rejected: a captured SynchronizationContext, since AppServices is constructed mid-composition where the context may be null or a pool context, so a capture could silently degrade to raising on the watcher thread. Marshalling at the source makes every current and future ConfigReloaded subscriber safe by construction. Headless tests keep the unchanged inline path (Application.Current is null). Guarded against shutdown races with HasShutdownStarted plus a narrow catch.

Before
An external config.yaml/.env edit with the Overview panel open threw NotSupportedException from WPF's CollectionView on the watcher thread and killed the process.
After
Reload work stays off the UI thread; only the notification hops to the Dispatcher.

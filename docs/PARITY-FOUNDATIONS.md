## 1. Settings store - `AppSettingsStore`

**For:** every persisted app setting, in one file, `%LOCALAPPDATA%\DefenseClaw.App\settings.json`. Typed sections: `Appearance` (style, mode;
still owned by `AppearanceService`), `Monitoring` (`HealthIntervalSeconds` 2-60, default 5; `Paused`), `Notifications` (`Critical`, `High`,
`Gateway`, `HighWaterUnixNano`), `Startup` (`GatewayAutoStart`, `CloseToTray`, `RememberLastPanel`, `LastPanelId`), `Connection`
(`CliPathOverride`), `Updates` (`LastCheckUnix`, `DismissedVersion`, `NotifiedVersion`; written by `UpdateWatcher`), `Palette` (`RecentCommandIds`: the last 5 command-palette command ids, newest first; section 14), `Seen` (one marker per stream panel, `audit` / `activity` / `ai-discovery`: where the operator last looked; section 15).

```csharp
var interval = Services.Settings.Current.Monitoring.HealthInterval;                  // read: cached, any thread
Services.Settings.Update(s => s with { Monitoring = s.Monitoring with { Paused = true } });   // change: atomic, persisted
Services.Settings.Changed += (_, e) => { if (e.Affects(AppSettingsSections.Monitoring)) Apply(e.Current.Monitoring); };
```

- One store per file per process (`AppSettingsStore.ForPath`), so its lock is the only writer; `FileAppearanceSettingsStore` is a thin client of it.
- Only the sections an update changes are written, into the file as it is on disk: unknown sections/members and a newer `schemaVersion` survive; the write is temp-file + flush + move.
- Never throws for what is on disk: missing/empty/corrupt/wrongly-typed content reads as defaults (per field); a failed write returns `false` from `Update`, keeps the change in memory and retries it with the next write. A file another process holds for a moment (a virus scanner, an indexer) is waited for first: the read of the file, the move over it and the removal of the temp file are each tried up to 4 times, 20, 40 and 60 ms apart (120 ms at most for one; the reads wait only for a sharing or lock violation, so a file that cannot be read for good fails at once), so that a hold of a few milliseconds is not "could not be saved" on the Settings page.
- `Update` writes synchronously (a few ms: the flush is what makes it crash-safe), so do not call it per keystroke or per frame - set a value when the operator commits it, or coalesce (e.g. remember `LastPanelId` when a panel activates, not while it scrolls).
- `Changed` is raised on the thread that called `Update`, after the lock is released; marshal to the UI thread if you touch controls. The `change` function must only build a value (no I/O, no call back into the store).
- Adding a section needs no migration: a section the file lacks is its defaults. Extend `AppSettings`, `AppSettingsCodec` (one read, one write) and `AppSettingsSections`.

## 2. Navigation requests - `ShellNavigation` / `IAcceptsNavigation`

**For:** "show this panel, and tell it this" (the Mac's `openAlerts / openAudit / openLogs`). A request is `{ PanelId, Payload }`; payloads today:
`AlertsFilter(SeverityFloor?, Kind?)`, `AuditPreset(Name)`, `LogsPreset(Name)`, `RegistryFocus(EntryType, Name, SourceId?)` (the Skills and MCPs "Open in Registries": the Entries tab narrowed to that entry, the source's row selected; CUST-276, see `RegistriesPanelViewModel.Entries.cs`). A target panel ignores payloads it does not understand.

```csharp
RequestNavigation("alerts", new AlertsFilter(AuditSeverity.Critical));              // from any panel view-model (or Services.Navigation.Request(...))
public sealed partial class AlertsPanelViewModel : PanelViewModelBase, IAcceptsNavigation
{ public void Accept(object payload) { if (payload is AlertsFilter f) { SeverityFloor = f.SeverityFloor; _ = ApplyFilterAsync(); } } }
```

- Exactly one request is outstanding; a second replaces one nobody has taken. It is **consumed once**: the catalog hands it to the panel when that panel *activates* (or at once if it is already on screen) and never again.
- `Accept` runs on the UI thread **right after `OnActivated`** (subscribed, active), including on the very first visit where `InitializeAsync` may still be running: apply the payload to state the load will honour. An exception from `Accept` is traced and swallowed.
- A request for a panel that is not built, or is in a hidden/minimized window, waits in the inbox. The shell shows the dashboard (building it if the session is tray-only) and selects the panel; a new window opens on `PanelCatalog.InitialPanel`. An unknown panel id is dropped with a trace.
- The status strip / tray can raise one without a panel: `MainWindowViewModel.RequestNavigation`, `OpenPanelCommand` (`CommandParameter="alerts"`), `ShellActions.OpenPanel`.
- A panel can also ask the shell for its command palette (the Overview's Diagnostics menu): `Services.Navigation.RequestPalette()` raises `PaletteRequested`, which the dashboard window answers by opening the palette. It is not a panel request, so nothing waits in the inbox.

## 3. Alert counts - `AlertQueueReader` / `AlertCounts` / `AlertCountsService`

**For:** the Mac's single "unacknowledged findings" number, so the sidebar badge, status chip, tray and Alerts panel agree. The definition
(`AuditStore.alertQueueEvents`): the newest 500 `audit_events` with severity CRITICAL/HIGH/MEDIUM/LOW, `bucket IS NULL` *or* `security.finding` + `finding.observed`,
`action NOT LIKE 'dismiss%'`, and not in `alert_acknowledgement_projection` (table may be missing). So the count caps at 500 (`HasMore` says "500+").

```csharp
Services.AlertCounts.Changed += (_, e) => Badge = e.Counts.TallyFor(Services.ConnectorScope.Allows).Total;  // subscribing starts it; leaving stops it
await Services.AlertCounts.RefreshAsync();                                          // after an acknowledge: badge drops now, not in 30 s
var newest = (await Services.AlertQueue.ReadAsync(newestLimit: 500)).Counts.Newest; // raw read: Id, Severity, Action, Target, Connector, Timestamp
```

- `AlertCounts`: `Tally` (per severity), `Total`, `HasMore`, `Newest` (first N rows), `ByConnector`, `TallyFor(allows)`, `SameAs`. `Source` is `Database`, or `Gateway` when the database predates schema v8 (no `bucket`): then the counts come from the monitor's already-fetched `/alerts` list (25 rows, so `HasMore` is usually set) - no extra request.
- The service refreshes on `GatewayMonitor.AlertCadenceElapsed` (the 30 s alert cadence, raised after the poll is published, independent of the gateway being up), once when the first subscriber attaches, and on `RefreshAsync`. **No subscriber, no work**: it is detached from the monitor and runs no query. `Changed` (UI thread) is raised only when what a badge shows differs, on first data, or when the counts turn unavailable/recover. A failed read keeps the last good counts and sets `Unavailable`; it never zeroes the badge.
- Read-only (`Mode=ReadOnly`), off the caller's thread (`ReaderOffload`), with a timeout (default 10 s; `Services.ReaderTimeouts` holds the app's limits for the audit readers - 10 s for this queue, 8 s for the inspector lookups, 5 s for the counts - and only an isolated test composition can be handed others) and cancellation that interrupt the running statement. Query plan is pinned by tests: two index searches (`idx_audit_event_name_timestamp` / `idx_audit_bucket_timestamp`) merged, no table scan. On the live 6.7 GB database: ~4 ms warm (the Mac's single-statement form is ~55 ms).

## 4. Connector scope - `ConnectorScope`

**For:** the one "All / one connector" filter every screen shares (the Mac's `connectorFilter`). Every connector-tagged panel follows it (override `PanelViewModelBase.OnConnectorScopeChanged`, filter with `Allows`); each page toolbar's ConnectorSlot holds `ctl:DcConnectorScopeChip Model="{Binding ConnectorChip}"` (shown with more than one connector); Ctrl+Shift+M cycles it. Audit and the Govern catalogs keep their combos as views of the same scope.

```csharp
var rows = allRows.Where(r => Services.ConnectorScope.Allows(r.Connector));          // the predicate; null scope allows everything
Services.ConnectorScope.Cycle();   // All -> first -> second -> ... -> All     (Set("codex") for a menu pick; Connectors is the roster)
Services.ConnectorScope.Changed += (_, _) => Refilter();                              // scope or roster changed
```

- Roster = `GatewaySnapshot.ActiveConnectors` (configured first, then live). The scope **resets to All by itself** when its connector leaves the roster or the roster shrinks to one or none; `Set` refuses a connector not on the roster; `CanScope` (roster > 1) is what shows the chip.
- An explicit scope is an exact match (ignoring case/padding) and **hides rows with no connector**, like every other Mac screen.

## 5. Runtime detection and gating - `Services.Runtime` / `RuntimeGate`

**For:** showing something only newer DefenseClaw runtimes have (verified against source commit 95159fd, which self-reports 1.0.0) and nothing else. 0.8.10 is the baseline: a feature it already has is never gated.

```csharp
if (Services.Runtime.Check(RuntimeCapability.AcpGuard).IsAvailable) { /* offer it */ }       // GateDecision: IsAvailable, Reason
var why = Services.Runtime.Check(RuntimeCapability.Sandbox).Reason;                            // "Requires a compatible DefenseClaw runtime (verified against source commit 95159fd)"
Services.Runtime.Changed += (_, _) => Rebuild();                                               // UI thread; first answer, upgrade
new PanelDescriptor(..., Requires: RuntimeCapability.AcpGuard)                                 // palette "Go to" row is disabled with the sentence until it is true
RuntimeGate.CheckSetupCommand(Services.Runtime.Capabilities, "kiro")                           // setup --help names it
```

- **Capabilities** (`PolicyModel`, `AcpGuard`, `RedactionAdvanced`, `Sandbox`, `CanonicalSchema8`, `TuiRegistry`, `AiRuntime`) are decided by `RuntimeProbe` from `--version-json` plus the `Commands:` lists of `--help` screens (the Mac's test). Markers are listed by `RuntimeCapabilityCatalog.Marker` and shown in About; each is absent on 0.8.10 and present at the pin. `CanonicalSchema8` also needs version 1.0.0 or later. `TuiRegistry` is the command markers (`setup` lists amp, devin, kiro), not a count of entries. `AiRuntime` (the Runtime panel, CUST-309) needs two screens: `agent discovery --help` lists `runtime` (0.8.10's lists disable, enable, scan, setup, status) and `agent discovery runtime --help`, probed only then, lists `status`, `scan`, `findings` and `permissions`. The subcommands that second screen lists are kept too, one by one (`Capabilities.HasAiRuntimeCommand("scan")`, like the Mac's `runtimeDiscoveryCommands`), so a runtime that lists `scan` but not `enable` offers Poll now and not Enable.
- **A gated panel is not just a disabled palette row.** `PanelCatalog.IsOffered(panel)` is the one test: the sidebar entry is hidden (and appears when the probe answers), the palette row is disabled with the sentence and shows no chord, `MainWindow.NavigateTo` and `PanelCatalog.InitialPanel` refuse it, and its number chord does nothing and is left out of the shortcuts list. The chords count in `PanelCatalog.ChordOrder` - the panels that need nothing in sidebar order, then the gated ones - so a panel that appears in the middle of the sidebar moves no existing chord (Runtime is Ctrl+Shift+5; `ShellShortcuts.NumberedPanels` is 15).
- **Fail closed.** Nothing probed yet, a timeout, a missing CLI, garbage output: `Capabilities.Unknown`, every flag false, features hidden. A failure is never read as "empty".
- **A panel with two surfaces** (Policies, CUST-293; see `RUNTIME-COMPAT-95159fd.md`): when what a panel *is* depends on the runtime, it asks `Services.Runtime.WhenProbedAsync()` on its first visit (the app's own first probe is awaited when the service is running; a service nothing started answers at once, so a tool or a test never waits for a probe that will not come), picks its surface with `PolicyBackends.For(Capabilities)`, and re-decides on `Services.Runtime.Changed` while it is on screen. Unknown is the 0.8.10 surface, and that surface's view tree is exactly what it was (the newer one is built only when the runtime has it).
- **A panel whose newer fields are in the payload** (AI Discovery models, CUST-310; see `RUNTIME-COMPAT-95159fd.md`): no help screen marks it, so there is no `RuntimeCapability`. A column, a filter or a chip exists only when some model carries what it shows (the Mac has no probe for it either), and a runtime that sends none of it - 0.8.10 - gets the panel it always had. The gateway's own report (`GET /api/v1/ai-usage`) is read through the bounded read of the gateway client and only adds those fields to the signals the files list.
- **Cache** (`RuntimeDetector`): keyed by the CLI file's path, size and modified time (a container: its name, for a short window). Re-probed when the key moves (an upgrade is noticed by the 30 s background check) or on "Check the runtime again". An unknown answer is retried after 15 s. Probes run `--version-json` and `--help` only (the production runner refuses anything else), each with a 20 s limit and 45 s for the round, and never appear in Activity.
- **Developer runtime selector** (Settings -> Advanced, `developer.*` in settings.json, off by default; off is byte-for-byte the installed runtime): `Installed`, `Cli` (explicit defenseclaw.exe + `DEFENSECLAW_HOME` + optional loopback gateway address), or `Container` (`docker exec` + published loopback gateway + a read-only host copy of the data folder). It is read once at startup (`AppServices.CreateStartupPaths` -> `RuntimeEnvironment.CreatePaths`), so a change applies on the next launch; an incomplete or invalid choice starts the installed runtime. Container mode runs `defenseclaw` and `defenseclaw-gateway` through `CliRunner.RunNamedAsync` as `docker exec [-i] [-e NAME] CONTAINER TOOL ARGS`: environment values stay in docker's own environment (names only on argv), and the config editor refuses to write the copy (`DefenseClawPaths.DataDirectoryReadOnly`).

## 6. TUI command catalogue - `TuiRegistryCatalogues` / `CuratedCommandCatalog`

**For:** the command palette's CLI rows (the Mac sheet's "all 253 current TUI entries"): one row per entry of the connected runtime's own TUI command registry (`defenseclaw/tui/registry_data.py`: name, binary, argv, description, category, needs-argument flag, hint), with the TUI's names, so `scan skill --all`, `skills` and `skill list` are three rows for the commands operators already know.

```csharp
var catalogue = actions.CliCatalogue;                                  // ShellActions: 0.8.10's registry, or the pinned source's once the runtime shows RuntimeCapability.TuiRegistry
var offered = catalogue.Commands; var note = catalogue.HiddenNote;     // what Windows runs / "21 hidden on Windows"
var all = TuiRegistryCatalogues.For(Services.Runtime.Capabilities).Entries;   // every entry, each with its WindowsUnavailable reason or null
```

- **Generated, checked in.** `tools/gen-tui-registry.py` reads both registries (the installed 0.8.10 and the pinned source commit) as data with `ast` - nothing of DefenseClaw is imported or run - and writes `Core/Cli/TuiRegistryData.Generated.cs`: the entries plus, in its header, which runtime and file each came from (version or commit, path in the package, SHA-256 with LF endings, entry counts). `--check` compares without writing. The counts are 231 (0.8.10) and 253 (pin); a refresh that adds an entry, an option or a read-only command fails a test until someone has read what it does (`TuiRegistryCatalogueTests`).
- **Which registry.** Follows `Services.Runtime`: `TuiRegistry` present gives the pin's, everything else (0.8.10, a runtime that has not answered, one that failed to) gives 0.8.10's, which is never gated. The palette rebuilds in place when the answer changes.
- **Hidden on Windows.** Each runtime's own platform table decides (`setup <connector>` unless supported or preview; the sandbox group; the local stack controller): 232 of the pin's 253 are offered (its own `build_registry("windows")`), 210 of 0.8.10's 231 (the 0.8.10 CLI refuses the same things there). The palette says how many it hid and, in the note's tooltip, why, in the runtime's words.
- **Tiers and review.** Every row has a tier from `CommandTiers` (unknown is a change). Only a bare read on the allow-list (`CommandTiers.UnreviewedReadPaths`, plus the gateway's six: `status`, `provenance show`, `watchdog status`, `connector verify`, `connector list-backups`, `policy domains`) runs without a review; a read with an option or a typed value on it, and everything else, is shown in `CommandReview` first. Options on an argv are limited to `TuiRegistryCatalogues.ReviewedFlags`; the gateway is never run bare.
- **Arguments.** A hint that is one word (`<skill-name>`) or one choice (`<observe|action>`) opens a box in the detail pane: Enter asks for the value, a second Enter reviews `... -- <value>` (a name the CLI would rewrite, such as `~`, is refused first). A hint with more in it, and anything that asks questions at a prompt (`keys set`, bare `setup`, the registry's "interactive" commands), is copied for a terminal instead. `start`, `stop` and `restart` of the gateway go the tray's way.
- **Ids** are `cli.` plus the TUI name with its spaces as dots (`cli.skill.list`), stable across catalogues, so a remembered "last command" can find its row again.

## 7. Docker look for the local observability stack - `Services.LocalStack`

**For:** offering `setup local-observability` (the Setup hub card, and the palette's registry rows for `up | down | reset | status | logs` and the bare group) only while Docker can run it - Compose v2 present and an engine that answers - and saying the probe's reason otherwise. 0.8.10 runs the stack natively on Windows (`platform_support.local_observability_stack_supported`, see the comment on `WizardWindowsPolicy.LocalObservabilityTarget`), which is also why both TUI registries list it there (section 6: `tools/gen-tui-registry.py` reads that function), so nothing about it is hidden by name; the CLI's own preflight stays the authority and the probe's warnings (WSL 2, per-user install, edition, ...) ride along on the review.

```csharp
var gate = Services.LocalStack.Decision;               // GateDecision: IsAvailable, Reason ("Checking for Docker…" before the first answer)
_ = Services.LocalStack.EnsureFreshAsync();            // looks only if there is no answer yet or it is old (60 s for a yes, 15 s for a no)
_ = Services.LocalStack.RefreshAsync();                // looks now (the Setup page's Refresh)
Services.LocalStack.Changed += (_, _) => OnUiThread(Reapply);   // raised on the probe's thread, and only when the answer changed
WizardWindowsPolicy.NeedsDocker(target) / .CommandNeedsDocker(argv)   // which card / palette row is gated (url and env are not: they print constants)
```

- **One look, shared.** `DockerProbe` runs `docker compose version`, then `docker info` (the CLI's preflight order) - read-only, never starts, pulls or runs anything. The Setup card and the palette read the same answer, so they cannot disagree, and Docker is looked at once rather than once per surface.
- **Not a poll.** No timer. The hub asks when it comes on screen and on Refresh; the palette when it opens (`ShellActions.CheckLocalStack`, which asks only if the palette lists the stack's rows), and `MainWindow` rebuilds an open palette's rows in place when the answer changes. Concurrent callers join the look already running. Once there is an answer it keeps being given while a newer one is fetched, so a card does not flicker into "Checking..." on every visit.
- **Fail open on "could not look".** A probe that throws or cannot run is `DockerState.Unknown`, which does not close the feature (the CLI checks again); only a definite no (not installed, engine down, no Compose) does.
- **Rows and tiers.** The registry's `url` row never reaches Docker and is always enabled (`env` has no registry row). The bare group row is the CLI's `up` (its group callback invokes it, whatever the registry's one-line description says), so it is gated and reviewed as `up`. `CommandTiers.IsReadOnlyLeaf` names `status | logs | url | env` by exact path - `setup` would make each a change - and they are on the allow-list (section 6): the three registry reads run without a review, `up`, `down` and the bare group change state, and `reset` is destructive (the registry's argv carries the `--yes` that stands in for the CLI's "Continue?", and the review says so).
- **Reviews say what the verb does.** `LocalStackReview` is shared by the palette's confirmation and the wizard's last page: the files `up` refreshes, the data `reset` deletes, the destination `down` leaves enabled, the Docker look's cautions, and a gateway restart only for the verbs that rewrite config.yaml (`up` unless `--no-config` or `--no-wait`; `down --disable-config`), from the `setup` group's result callback in the CLI's source.

## 8. Change probe and oversized rows - `AuditChangeProbe` / `OversizedValue` (CUST-284)

**For:** "has `audit.db` changed since I last looked?" answered by one trivial statement, so a refresh that finds nothing new costs a probe and not a query, a decode and a diff; and "a value too big to load is *unavailable*, not cut off and not an empty list" (the Mac 1.1.26's unchanged-snapshot skip and `lastQuerySucceeded = !rows.isEmpty`).

```csharp
var before = await Services.AuditChanges.SampleAsync(ct);                    // an opaque AuditStamp, taken BEFORE the read
var rows = await Services.Audit.QueryAsync(query, ct);
if (!(await Services.AuditChanges.SampleAsync(ct)).Matches(before)) { /* something was committed since: read again */ }
```

- **What shares it.** `AppServices` builds one probe over the live file and hands it to `Audit`, `AlertQueue`, and the readers the Mutations tab, the Logs streams and the Alerts egress feed build (`new MutationReader(path, Services.AuditChanges)`). Each reader remembers its last answers by query/limit/stream under the stamp it took *before* reading (`SnapshotMemo`); a call that finds the same stamp returns the remembered **object** (no connection, no statement, no row decoded; `UnchangedReads` counts them, `RowsDecoded` the rows that were), so a view-model can tell "nothing changed" by reference. A commit that lands between the stamp and the statement makes the next sample differ, so the worst case is one read too many, never a stale one. Unknown stamps (no probe, missing file, a database that could not be sampled) match nothing; failed and cancelled reads store nothing; a remembered answer is not trusted past 5 minutes (backstop only). The Audit live refresh (CUST-262, section 12) polls `SampleAsync` and fetches only when the stamp moved: it needs no timer of its own beyond its poll.
- **Why `PRAGMA data_version` on a kept read-only connection** (the alternative was the size / modified time of `audit.db` and its `-wal`): it is exact in rollback-journal and WAL mode, never reads a table page (the same cost on 0.6 GB and 10.4 GB: 0.08-0.13 ms for a whole unchanged read, probe included), holds no transaction between statements (a `wal_checkpoint(TRUNCATE)` still completes, pinned by a test), and a writer committing as fast as it could was never missed (0 of 241). File metadata is not exact on this platform: the WAL is *reused* after a checkpoint, so its size stops moving while the content keeps changing (73 of 241 commits left the length unchanged), and the modified time is a coarse clock tick (2 of 214 commits 20 ms apart looked like none). A wrong "unchanged" leaves a screen stale; a wrong "changed" only costs a read. The kept connection adds no pin that was not there: the readers' pooled connections hold the file for the life of the process too (measured: still held 200 s after `Close()`, released only by `ClearAllPools`). `Release()` closes it for a caller that wants the file back; the next sample opens a new connection with a new epoch, and every older stamp is then stale. No timer, no thread: it does something only when asked.
- **The archive (CUST-299) is a file stat.** An `immutable=1` reader gets a probe of its own: the stamp is the file's size, modified time and creation time (a replaced archive moves them); nothing is opened, locked, created or written beside it.
- **Oversized rows.** Wherever a reader limits a payload, a value over the limit is left in the database - decided by `octet_length`, which reads the record header and not the value (100 rows of which 12 held 2 MB: 0.2 ms, against 26 ms for `length(CAST(x AS BLOB))` and 28 ms for `substr`) - and the row is returned with its column empty and `Oversized` naming the column, its size and the limit (`structured_json is 3.2 MB, over the 256 KB limit`); its other columns are intact. Limits: `AuditReader` `details` / `structured_json` 256 KiB each (`AuditQuery.PayloadLimitBytes` lifts it for an export, which must not drop text), `MutationReader` 256 KiB per before / after / diff / reason / record, `EventStreamReader` 64 KiB of `payload_json` (the existing `PayloadOmitted`, now with the reason), `NetworkEgressReader` 64 KiB. Mutation and egress values used to be `substr`-cut: a document cut mid-way reads as a different one (an egress decision was read as "not allowed"). A page of rows that are all oversized is a page of rows (`AuditPage.AllOversized`), never "no events": the Audit panel lists them, says why in the Details cell and the inspector (in a code box as `(not shown: ...)`, broken into lines that fit it by `OversizedValue.Placeholder(width)`: the boxes scroll sideways, and one long line is cut off under the scroll bar), and the filter strip reads `1 event too large to display`; Alerts and Mutations say the same in their notes; the Logs raw JSON carries `payload_unavailable`.
- **What the panels do with an unchanged answer.** Audit: a fresh load that reads the page and total already shown (same ids, same order) leaves the rows, the selection and the scroll position alone; "Load more" extended the list, so a refresh still starts over from the newest page; the time window starts on a whole minute so two refreshes inside it ask the same question. Alerts: a queue read that finds the same finding and egress ids rebuilds nothing (no hydration, no filter pass). Mutations: the same changes leave the list alone. Logs: the reader hands back its last list, and a row already projected is reused by id, so a read after the database moved (it does all day) parses and masks only the rows that arrived.
- **Measured** (synthetic database from the real DDL, 1.25 M audit rows, 10.4 GB; ms per read, wall / CPU; the unchanged column includes the probe): alert queue 11.1 / 12.5 -> 0.13 / 0.16; mutation history 16.9 / 16.3 -> 0.12 / 0.10; Verdicts stream 171 / 247 -> 0.12 / 0.10 (a read after the database moved: 125 / 117, the id reuse); Events stream 82 / 84 -> 0.08 / 0.10; Audit page of 100 + 24 h total 20.7 / 23.1 -> 0.09 / 0.16; egress feed 1.6 / 1.9 -> 0.08 / 0.10. A read after a *change* costs what it did (the probe adds ~0.04-0.07 ms). The probe: 3 ms to open and first sample, then ~40-70 us per sample at either size.

## 9. Catalogue trust and the config disk signature - `CatalogTrust` / `ConfigDiskSignature` (CUST-283, CUST-312)

**For:** "may the rows on screen authorize a change?" Skills, MCPs, Plugins and Tools (`GovernPanelViewModelBase`), Registries, and Policies (the 0.8.10 table and the model surface, `PolicyModelViewModel`) each own a `CatalogTrust`; the Runtime panel's STALE snapshot follows the same rule with its own flag. The Mac's Policies counts as current only while the installation and the `config.yaml` / `.env` disk signature are the ones the read saw (`PoliciesView.swift:25-29`); here that is the config half (the installation half is the guard of section 10).

```csharp
Trust = CatalogTrust.Watching(services.Paths);        // in the panel's constructor: the list goes stale when config.yaml or .env change
Trust.BeginRead();                                     // where a read really starts: notes the files' signature for the rows it produces
Trust.MarkComplete();  // or MarkPartial(diagnostics) / MarkFailed(message)
Services.ConfigReloaded += OnConfigReloaded;           // OnActivated (and -= in OnDeactivated): if (Trust.CheckConfig()) NotifyTrust();
if (Trust.ReasonNow() is { } why) { /* refuse */ }     // at the moment a change is requested or confirmed
review.RunGuard = () => /* the same, at Confirm */;    // DiscoverActionReview: nothing runs when it answers
```

- **What turns changes off** (`Trust.Reason`, one sentence for the tooltip; the rows stay for every one, and Info, Copy name and Refresh stay on): the first read still running, a partial read (the CLI named a source it could not read), a failed refresh (the last good rows stay, labelled), a read older than 10 minutes, and - CUST-312 - a read made before `config.yaml` or `.env` changed. A fresh complete read restores trust.
- **The signature is a stat.** `ConfigDiskSignature` is the path, whether it exists, the length and the last-write time (UTC) of each file - the Mac's rule (`InstallationContext.diskSignature`: path, modified time, size) - taken with `FileInfo`. Nothing opens, reads or hashes either file: `.env` holds the gateway token and every key `keys set` stored, so the type has no member that could carry content (a test pins its shape and takes one of an exclusively locked file). The config watcher's own `FileSignature` hashes small files so it can tell two same-length saves apart; the trust deliberately does not use it. A same-length save inside one file-system clock tick is not seen by a stat - the Mac has the same limit - and only matters for an edit made within a few milliseconds of the read on screen.
- **When the files are looked at** - only when something happens, never on a timer and never from a bound property (`IsTrusted` and `Reason` are pure; rows ask them for every cell): a read starts (`BeginRead`) and ends (`MarkComplete` / `MarkPartial`; files that moved while it ran make the rows stale at once, because nothing says which side of the edit it saw); `AppServices.ConfigReloaded` is raised while the panel is on screen; the panel comes back on screen (a change made while it was away); and a change is requested or confirmed (`ReasonNow`), which is what covers the gap before the watcher has spoken. Two stats each.
- **No new watcher, timer or poll.** `ConfigChangeToken` already watches both files (a directory watcher with a 2 s poll as backstop) and `AppServices` raises `ConfigReloaded` for either, on the UI thread, so `.env` needs nothing of its own. Panels subscribe only while active (`OnActivated` / `OnDeactivated`), like every other subscription. The event is *compared*, not believed: a panel that re-reads straight after its own change (the CLI rewrote `config.yaml`; Registries also calls `ReloadConfig()`) is not made stale by the watcher's notification, which arrives a few hundred milliseconds after the read began. A test fixes that no type of the rule owns a timer, a watcher or a thread.
- **What stale does.** The rows stay; every action is off with `CatalogTrust.ConfigChangedReason()` - *Changes are off: config.yaml or .env changed after this list was read. Refresh to act on current data.* (the Policies model surface says "these settings"; the Runtime panel's STALE banner says the snapshot was read before the file changed) - as the buttons' and menu items' tooltip, the same place as every other reason. Govern and Registries do not read on the event (Refresh does) but read once on the next visit if they are stale, as they do for an old list; the Policies model surface reads by itself when idle (CUST-293).
- **Refused at execution.** A change started after the edit is refused when it is requested (`RefuseUntrustedChange` / `RefuseChange`, result bar or notice) and again when it is confirmed: the Govern panels in `ConfirmYes`, every review through `DiscoverActionReview.RunGuard` (Registries, Policies, the model surface, Runtime). Nothing starts; the dialog finishes with *Not run. <reason>*, and `CliRunner.RecordRefusal` writes the command that was refused into Activity - no exit code, `refused - <reason>`, badge "refused", its argv checked for secrets like any run's (an argv that holds one is refused and not recorded). The follow-up of the review (`onFinished`) is not called: nothing ran.
- **Runtime panel.** It keeps its own stale snapshot (`MarkStale`, the STALE banner, the note under the buttons, `BlockedReason`) and records the signature per read the same way; Poll now, Enable and Disable are off while it is stale for any reason, and a review confirmed on a snapshot that went stale is refused.
- **For the next panel with a list that actions are taken on:** construct the trust with `CatalogTrust.Watching`, call `BeginRead` where the read starts, subscribe while active, ask `ReasonNow` before a change and set `RunGuard` on its `DiscoverActionReview`. `CatalogTrust` needs a signature source for the config rule; `new CatalogTrust()` has none, which is what the existing age tests use.

## 10. Installation context and the read-only guard - `InstallationContext` / `InstallationGuard` / `InstallationGate` (CUST-308)

**For:** "which DefenseClaw is this run driving, and may the app change it?" The Overview's Blocks and Hook Calls tiles therefore land on every block and every hook call. The switch is a view setting beside the filters: Reset filters and a switch between Live and Archive leave it as it was set.
- **Events and the TUI's v8 buckets.** The Events stream reads every canonical bucket but `telemetry.ingest`, so each of the TUI's seven (`EventStreamReader.AlertBuckets`: `security.finding`, `guardrail.evaluation`, `enforcement.action`, `asset.scan`, `network.egress`, `platform.health`, `diagnostic`) is in it; the *Verdicts* stream is the Mac's narrower decisions list and still leaves `network.egress` out. What was missing was the rows' own words: an egress row now shows its decision (`defenseclaw.network.decision`, then `policy_outcome`), target and reason, a scan row its `scan.verdict`, and an egress event is kind `egress`, so the Event picker finds it. Same as the TUI: `signal = 'logs'` only, payload at most 64 KiB (`PayloadByteLimit`). Different, on purpose: the stream reads the newest 1,000 events (the Mac's window) where the TUI's Alerts reads the newest 500 of its 1,000, and it does not read `projected_record_json`'s `outcome`.
- **Alerts -> Events.** The Alerts strip has an **Events (all activity)** button (`AlertsPanelViewModel.OpenEventsCommand`) that sends `LogsEvents` to `logs`; the Logs panel opens on Events from a clean slate (default preset, no search, any severity, every action and event, no telemetry) on the actionable view. It changes nothing in Alerts.
- **Audit live refresh.** While the panel is on screen (`OnActivated` to `OnDeactivated`; one catch-up poll on coming back; never for the archive) a `DispatcherTimer` ticks every 5 s (`LivePollInterval`). A tick takes `AuditChanges.SampleAsync` and compares it with the stamp taken before the list was last read: **unchanged is the whole cost** (one `PRAGMA data_version`; no page, no count, no row decoded - the test holds the reader's counters still). Changed: one page of the list's own query, from `LateCommitWindow` (5 min) before the last look - *not* "newer than the newest row": on a real database 5% of rows were committed behind a newer one, up to 112 s behind, and most of them are scan findings. Rows the list does not know are inserted where the query's order puts them (the objects already listed stay the same objects: selection, inspector, and - through `LiveRowsInserted` - the scroll offset, which the view adjusts by the height inserted above the row being read); a row older than the last one a load read is "Load more"'s, so none is listed twice; a low-signal row is counted once (`_liveHidden`); more than `LiveWindowLimit` (2,000) rows in the window starts the list over from the newest page. A tick that finds a load running does nothing and a load that starts cancels a poll in flight. A failure keeps the rows, says "Live refresh paused (reason)" beside the "Updated hh:mm:ss" caption and backs off 5, 10, 20, 40, 60 s.
- **Tests.** `ActionableRuleTests` (the TUI's table), `ActionableAuditPagingTests`, `EventStreamActionableTests` (buckets, egress/scan words, actionable per row) in Core; `EventsViewTests`, `EventsViewRenderTests` (the switch, the chip, the Alerts button), `AuditActionableTests`, `AuditLiveRefreshTests` (the acceptance: a block event in the next poll, an idle poll is one probe sample), `AuditLiveRefreshViewTests` (the timer, the scroll offset) in the App suite.

## 13. The observability plan and what may be shown of an address - `ObservabilityPlanReader` / `EndpointDisplay` (CUST-272)

**For:** the Overview's Observability card, which is the TUI's: the compiled routing plan merged with `/health` by destination name, plus the Local SQLite line. The pieces are in Core so another surface (a status-strip chip) can use them: `ObservabilityPlan.RedactionSummary` is the TUI's aggregate label (`per-route · unredacted`), and `OverviewPanelViewModel.RedactionSummary` carries it to the Configuration card.

```csharp
var read = await vm.PlanReader.GetAsync(force: false, ct);            // ObservabilityPlanRead: Ok + Plan, or a status and one sentence; never throws
read.Plan!.Destinations[0].RedactionLabel                             // "unredacted (none)", "redacted: sensitive", "mixed: none, strict", "not-applicable"
ObservabilityConfigFacts.FromConfig(Services.Config).RetentionDays   // observability.local.retention_days; null when config.yaml is silent
EndpointDisplay.Host("https://user:pw@collector.example.test:4318/v1/logs?key=k")   // "collector.example.test:4318"
```

- **What is read from where.** `defenseclaw observability plan --format json` carries the rows (one per bucket, signal and destination, with the plan's decision) and the delivery limits; it names destinations and never addresses, and carries no retention, path or judge-body setting. Those are `config.yaml`'s (`ObservabilityConfigFacts`, read from the text the app already holds: retention, `observability.local.path` / `judge_bodies_path`, `guardrail.retain_judge_bodies` - on unless config says otherwise - and each destination's host). What a destination is doing now - its state, queue, last delivery - is `/health`'s (`DestinationHealthReader`: closed tokens, counters and timestamps only). The TUI gets all of it from the gateway's `config-v8 effective` helper, which prints addresses and is not on the read-only list; `config show --effective --section observability` prints them too. The plan document is the one source that cannot carry a credential.
- **Read-only, off the UI thread, bounded, cached.** The argv is `observability plan --format json` (`CommandTiers`: read-only; a test holds both runtimes' command trees to it). The run starts on the pool, is stopped after 30 s (`TimedOut`) and lands in Activity like any command. The answer is reused until it is 5 minutes old, until `config.yaml` is replaced (the reader is built with `() => Services.Config`, which is swapped wholesale on every reload, so a plan is never served for a configuration it was not compiled from), until Refresh forces a read, or until `Invalidate()`; a read that was running when the configuration changed is run again. A failed read is served for a minute, so a missing CLI costs one attempt a minute and not one per 5 s poll. Callers share one run; a caller's token stops that caller waiting, not the run.
- **Merge and fallback states.** The plan's destinations come first, each merged with its `/health` entry by name (without case), then the entries the plan does not list, then the sinks. The gateway's word for the state wins; a plan destination the gateway does not report is `disabled` when its policy is off and `unavailable` when it is on (the TUI's two fallbacks). A plan that cannot be read leaves the card exactly as it was before the plan existed, with a one-line note (and the Local SQLite line, which belongs to the effective view, is not drawn).
- **No address is shown whole.** `EndpointDisplay.Host` reduces an address to `host[:port]` by hand (not `Uri`, which drops default ports and reads `//host` as a share): userinfo, path, query and fragment are gone, so a token in a path is not shown either, and an address it cannot vouch for (a bad port, odd characters, an `@` in the path - a password with a raw `/`) is `<unreadable endpoint>`, never the raw text. The raw value is dropped while config.yaml is read, so nothing built on `ObservabilityConfigFacts` can show it. The gateway's own sentences about a failure (`reason`, `last_error`) pass `EndpointDisplay.ScrubText` (every URL cut to `scheme://host[:port]`, then `DisplayRedaction.Prose`); the structured `/health` fields only ever cross as closed tokens.
- **Retention matches config.** `observability.local.retention_days` wins; where config.yaml is silent the window is the one the running gateway reports (the runtime's default: 90 days at 0.8.10, 7 at the pin), and where both are silent it says `runtime default` - no default is encoded in the app.
- **Counting buckets.** The plan has a row per bucket and signal, not the route's selector, so `Buckets n/N` counts the buckets with events routed to the destination under the current collection settings (a bucket that collects nothing is not counted, which the TUI's route-only count does); a route the plan cannot settle without the event (a severity, a source) counts and makes the redaction label say `(+ conditional routes)`, because its profile is not in the document.

## 14. Command outcome, Rerun and palette recents (CUST-264)

**For:** the Activity panel's footer and Rerun (the TUI's `meta_footer`, `suggested_next_action` and `!`), and the command palette's recents, "Re-run last command", "Cancel running command" and initials matching.

```csharp

CommandNextAction.For(executable, argv, exitCode)                                   // "review readiness", "open readiness or rerun doctor", ... or ""
```

- **Outcome line** (`ActivityRow.MetaText`, set once when the row first sees its run finished; a later run never changes it). Each part is claimed on evidence. *config reloaded*: exit 0 and a `defenseclaw setup | guardrail | settings | init | registry` command (the TUI's list), unless `CommandTiers` calls it a read (`guardrail status`, `registry list`, `--help`, `--dry-run`; the TUI says it of those too), or the gateway restarted. *gateway restarted*: exit 0 and `CommandReview.RestartsGatewayFor(argv)` - the rule the review states before the run, so an unknown `setup` verb says yes, as the review does - or `defenseclaw-gateway restart` itself; the TUI observes the gateway's `started_at` instead, which a row cannot. *doctor cache refreshed*: a `doctor` run and `doctor_cache.json` written between the run's start and its end (+2 s: the file is written before the process exits, passing or failing; nothing else writes it, 0.8.10 and the pin). One stat, only for a doctor row, only when the run has finished. *next:* is `CommandNextAction`, the TUI's table over its label (the tool and the first two words that are not options, stopping at `--`, where a name from outside starts); none after a cancel. A run that never started (a refusal), was handed to a terminal, or is not a DefenseClaw command (cosign, the installer) has no outcome.
- **Rerun** (`ActivityRow.RerunCommand`) opens the shared review (`GatewayActionDialog` over `CommandReviewControl`) for the entry's exact argv on its own tool, at the tier the row shows, and runs it once confirmed: a destructive entry opens focused on Cancel with the danger confirm, like every destructive review. The runner is told to refuse a name the CLI would rewrite, and a parsed JSON read keeps its whole output. Off while the run goes (the button stays, with the reason as its tooltip); absent for an entry that carried a stdin or environment secret (the app never kept the value), the app's own signature checks and the installer, a command handed to a terminal, a refusal (ask again from the panel, whose list the guard found out of date), and any `defenseclaw-gateway` run with no argument (a bare one starts a second daemon). The gateway's start / stop / restart are reviewed in the tray's words; a confirmed stop is the operator's word (`GatewayAutoStart.MarkUserStopped`) and the status strip is refreshed after any of the three.
- **A read-only installation (section 10) comes first.** `CommandRerun.ReviewFor` is built through `GuardedBy` like every other review: for a state-changing or destructive entry on a managed or invalid installation the review carries the installation's sentence (a *State-changing actions disabled* bar, Confirm off - a destructive one still opens on Cancel), and a read's review is the same as ever. The entry's Rerun is **drawn but off** with that sentence as its tooltip and help text (`CommandRerun.InstallationBlockOf` asks the same `InstallationGate` the runner enforces, so a read - `doctor`, `skill list`, `status`, `watchdog status`, `connector verify`, `policy domains` - can still be run again, and a change cannot), ahead of "wait for this command to finish": one reason per control, the installation's first. An entry that has no Rerun at all keeps the sentence that says why. The panel follows the installation (`ActivityPanelViewModel.OnInstallationChanged` asks every row again, because a finished row is not ticked), so the buttons turn off when config.yaml turns managed and on when it is fixed. `RunAsync` says the sentence and shows nothing when it is reached for a blocked entry anyway (a row or palette drawn before the flip), asks again after the operator confirms (a review that stood open while the installation flipped runs nothing, records one refusal in Activity and does not take a confirmed stop for the operator's word), and the runner refuses whatever this class did; a run the runner declined is reported as *Not run*, never as *Ran ... again*.
- **Palette recents.** `settings.json` `palette.recent`: the last five ids of commands the palette ran, newest first (`PaletteSettings`, `AppSettings.Palette`; blank, repeated, over-long and non-string entries are dropped on read, so a hand-edited file is cleaned). An empty search lists them first, newest first, with a "Recent" chip; a typed one ranks by what it matches. A recent command that cannot be chosen now stays among them, greyed out, with the reason in place of its description - the installation turned read-only since it was run (its sentence, which comes first: this includes the Splunk dashboards' rows, whose Terraform look is the next reason), Docker or Terraform went away, the gateway is not running - and Enter and the arrow keys skip it to the first recent that can be chosen. Ids, never titles or command lines: an id that no longer names a row is skipped, and a typed value is never stored. "Re-run last command" and "Cancel running command" are not remembered. A change to `Palette` alone (or to `Seen`, section 18) does not reload the Settings page's form (a half-typed path there would be lost).
- **"Re-run last command"** is the newest Activity entry that can be run again (by start time, skipping the ones that cannot), through the same `CommandRerun`; disabled, with the reason, while that entry still runs - and, on a read-only installation, while that entry would change it (the target decides: a newer read is the target and works; the installation's sentence is the reason even while the target runs, and "no command in Activity" is still what it says when there is none). **"Cancel running command"** stops the newest run that can be stopped (not the installer, not one already being cancelled) with `CliRunner.Cancel`, like the row's Cancel; it stays on for a read-only installation, since cancelling is not a change to it (`Cancel` is not a run and the gate does not see it). Both rows name the command in their description.
- **Initials.** A search term of two letters or more matches the first letters of a title's words (`rg` for "Restart gateway", `rlc` and `rrlc` for "Re-run last command", `slu` and `slou` for "setup local-observability up"), at 70: below the start of the title (100) and of a word (80), above a hit in the middle of one (60).
- **The gateway's fixed verbs** (`GatewayVerbs`): `watchdog start | stop | status`, `connector verify | list-backups | teardown`, `policy reload | domains`, each read from the 0.8.10 gateway's help screens (kept in `Fixtures/runtime-0.8.10/gateway`, and a test holds the list to them). Their rows come from the registry (section 6); the tier is `CommandTiers`' (`connector verify`, `connector list-backups` and `policy domains` are named in full there, since no verb in the shared vocabulary says they read; `watchdog status` is a read by its verb), the four reads run as they are, `watchdog start | stop` and `policy reload` are reviewed, `connector teardown` is destructive. On a read-only installation the generic override of section 10 (`BuildCliCommands`) covers them like any registry row: `watchdog start | stop`, `connector teardown` and `policy reload` are off with the installation's sentence - ahead of "still checking the gateway" and "the gateway is not running", whatever the gateway is doing - and a Run that arrives another way ends in that sentence as a toast, with no review; the four reads stay on and the runner lets them through.

## 15. Search tokens, correlation ids, hook rows, Current state, the Connector column - `SearchQuery` / `AuditQuerySearch` / `EnforcementStateReader` (CUST-261)

**For:** the 0.8.10 TUI's `field:value` search (`connector:`, `severity:`, `run:`, `id:`, `actor:`, `type:`, `target:` - its Audit panel takes ten, its Alerts and Logs panels only `connector:`), one parser for the three panels; the correlation ids an alert carries; a connector's hook call read from its details (`claudecode · preToolUse`, `allow · 320ms`); the Audit inspector's "Current State" of a skill, MCP server, plugin or tool; and the TUI's CONNECTOR column, shown only while more than one connector is active.

```csharp
var search = SearchQuery.Parse(box.Text);                      // every field; Parse(text, SearchField.Connector) is the Logs panel's
search.Tokens; search.FreeText;                                // [(Connector, "codex")], "block skill"
auditQuery = auditQuery.WithSearch(search);                    // Audit: the tokens become filters of the list's own query (SQL, bound parameters)
alertItem.Matches(search);                                     // Alerts: in memory, per field
StructuredDetailParser.HookTarget(target, details, column);    // "claudecode · preToolUse"
StructuredDetailParser.HookSummary(details);                   // "allow · 320ms" / "block · HIGH · 41ms"
StructuredDetailParser.InspectorRows(details);                 // the TUI's labelled rows, noise left out, yes / no
await new EnforcementStateReader(livePath).ReadAsync("skill", name, connector);   // "blocked" - one read-only seek on the actions table
```

- **Grammar** (`SearchQuery`, Core). Words are split on white space; a word is a token when what precedes its first colon is a field the caller recognises (case ignored: `Connector:Codex`; `run_id`, `trace_id`, `request_id`, `session_id` are accepted beside `run`, `trace`, `request`, `session`); the value is the rest of the word. A `"` opens a quoted stretch that runs to the next `"` (or to the end, while it is being typed): `target:"my skill"`; a word that starts with a quote is a quoted phrase of free text. Anything else - a word with no colon, `foo:bar`, a field the panel does not know - is free text, verbatim, and a token with no value (`connector:`, the name being typed) narrows nothing. **The free words are one phrase**, matched as a single substring as each panel always did (the TUI matches each word on its own); with nothing recognised and nothing quoted it is the typed text trimmed, exactly, so a search with no token in it behaves as before. Values keep their case; every comparison ignores it. "Show same target" types the target as plain text (`SearchQuery.AsFreeText`: quoted when it would otherwise read as a token).
- **What each field means.** `connector:` is a name matched whole (the chip's rule: a row with no connector is nobody's); every other token is a case-insensitive part of the column. Alerts: `severity` the stored spelling or its bucket, `run`/`trace`/`request`/`session` the ids, `id` the audit id, `actor` the source, `type` the kind (audit, scan, egress) or what the action is about, `target` the reference or the audit target, `details` the details, title or evidence. Audit: the column of that name; `type` is the TUI's TYPE (`AuditTargetType`: what the *action* names - `skill-block` is a skill, `scan-finding` a scan; the first rule wins, as the TUI's table) **or** this app's Type column (the bucket), so `type:skill` and `type:security` both find rows. Logs: `connector:` only; any other `field:value` is text to look for. Alerts' free text also covers the run, severity, source, connector, details and the three other ids (a trace id pasted from another tool finds its alert); Audit's free text is the search it always was (details, event name, tool, target).
- **Audit is SQL, all of it.** `AuditQuerySearch.WithSearch` maps the tokens onto `AuditQuery`: the first `connector:` is the query's own indexed `Connector` (the reader's walk-or-seek choice applies; the name is lower-cased, as connector ids are and as the TUI lower-cases the search), one the filter bar already holds or a second is an exact `FieldFilters` entry (ANDed, so two different connectors match nothing), the rest are `AuditFieldFilter(AuditField, value, Contains)` - `column LIKE $fieldN ESCAPE '\'` with `%`, `_` and `\` in the value escaped. The column comes from `AuditReader.ColumnOf`'s closed list and `type:` from a CASE built from `AuditTargetType.Rules`; **nothing typed is ever SQL**. Because it is the list's own query, the page, "Load more", the total (the fast severity counts skip a query that has filters), the live refresh (`MergeLiveAsync` reads `BuildQuery`), the export and the reader's remembered pages (the key holds the filters) all honour it with no code of their own, and no token needs the rows read and filtered in memory. A search of any kind pauses "Actionable only" (section 12). A LIKE walks the window like the free-text search does (1.4 s for 24 h on the live database, cancellable); `connector:` is an index.
- **Correlation ids.** The Alerts inspector's *Correlation* section lists Run ID, Trace ID, Request ID and Session ID (those the alert has: an audit row's four columns; the gateway's `/alerts` run and request id and, when it sends them, trace and session) as selectable mono text. **Copy details** of one alert is the TUI's multi-line `copy_detail_text`: `Severity:` (the bucket: WARN prints MEDIUM), `Action:`, `Target:`, `Timestamp:` (ISO 8601, UTC), `Details:` (the audit details; the title when there are none), then the ids; a connector-hook alert reads its decision, mode and timing as labelled lines. Several rows are copied one line each, as before.
- **Hook rows** (`StructuredDetailParser`, over the existing parser). The Target cell of a `connector-hook` row is `connector · phase` (the connector from the details, else the row's own column), the Details cell `decision · SEVERITY · elapsed` - the decision is `action` else `decision`, the severity only when it is not `NONE` (upper-cased), the time `elapsed` else `duration_ms` / `elapsed_ms` (the 0.8.10 gateway writes the latter: a bare number reads as `23ms`; the TUI looks only for `elapsed` and `duration_ms`). The inspector is titled `claudecode preToolUse` and its *Parsed details* are the TUI's `structured_detail_rows`: its key order and labels (`action` is *Decision*, `mode` *Enforcement mode*), `<redacted len=8 sha=...>` as its size and digest, `would_block` and `registry_configured` as yes / no, and `severity=NONE` and `would_block=false` while `mode=observe` left out - for any kv-shaped details, as the TUI does. `Pairs` and `SafeMetadataPairs` are unchanged. The row keeps its raw `Target` and `Summary` (copy, export and the underlying event are what they were); only the cells, the title and the screen reader's name read the hook form.
- **Current state.** Selecting an event whose action names a skill, mcp, plugin or tool (`AuditTargetType.IsGoverned`) and has a target reads that item's row from the live `actions` table - always the live database, also while the archive is on screen: the state is about now - and shows `Current state: blocked` (`blocked`, `allowed`, `quarantined`, `disabled`, comma-joined as the TUI's `ActionState.summary()`; `none` for an entry that does nothing; no line for no entry). There was no reader of the `actions` table in the app (the Govern panels get it through `<noun> list --json`), so `EnforcementStateReader` is one read-only seek (`idx_actions_type_name_conn`) with the Govern panels' vocabulary (`actions{file,runtime,install}`, `GovernJson.Interpret`'s words and tones) and the CLI's connector rule (`enforce/policy.py`: a connector's own fields win per field, the global entry fills in the rest; the TUI reads only the global one). It never starts a command, is bounded like the inspector's other lookups (`Services.ReaderTimeouts.Audit`: 8 s in the app, the suite's ceiling in a test composition), fails to nothing (a busy or older database shows no line), and a lookup overtaken by another selection cannot write over it.
- **The Connector column** (Alerts after Action, Audit after Type, as the TUI's): in the table only while `Services.ConnectorScope.CanScope` (a roster of two or more - the chip's rule, `ConnectorColumn`), so a one-connector install has exactly the columns it always had (the existing header tests hold). The view adds the column (a `DataGridTextColumn` kept as a resource) and takes it out as `ShowConnectorColumn` changes; the panel follows the scope's `Changed` while it is on screen, because a roster change is not a scope change and the base class's hook ignores it. `DcGridColumns` learned two things for it: a column that is not visible takes no share of the room, and a column that joins later (or returns) is learned with the weight it was declared with, not the width it was last given (`DcGridColumns.Refit` after a change). At the window's 940 DIP minimum the Alerts table still fits with the column (its floor is 64 DIPs); the Audit table's floors then add up to about 660 of 649 DIPs and the table scrolls sideways by a few.

- **Tests.** Core: `SearchQueryTests` (the parser table: quoting, unknown tokens, case; matching), `AuditQuerySearchTests` (each token on a real table, wildcards and injection text as plain values, totals, remembered pages, paging, the plan of a connector token), `ConnectorHookDetailTests`, `AuditTargetTypeTests` (also: the SQL CASE and the code agree), `EnforcementStateReaderTests`. ## 16. The Setup list editors - `SetupResourceViewModel` / `SetupResourceArgv` / `EndpointHost` (CUST-270)

**For:** the TUI's `SetupResourceEditorScreen` (observability destinations, webhooks) and `TrustedPathsEditorScreen`: a list with a state per row and the verbs that act on the selected one. SetupResourceWindow.OpenTrustedPaths(Services, owner, folder, "Setup of ... stopped: ...");   // the same editor, with the folder offered on a banner

- **The verbs, read from the 0.8.10 source and `--help`.** The lists are `setup observability list --json`, `setup webhook list --json` and `setup trusted-paths list --json` (the TUI reads the same data in-process; the app has no config model to read it from, and all three commands have the flag). The review states a gateway restart where the command causes one (`CommandReview.RestartsGatewayFor`; a test does not, and a trusted folder does only when it is in config.yaml) and warns when enabling a destination that sends content unredacted.
- **Reads: read-only tier, off the UI thread, bounded.** The list and Show go through `SetupResourceViewModel.RunReadAsync`, the one door the editor starts a command through on its own, which refuses anything `SetupResourceArgv.IsRead` does not recognise. Each read is limited to 60 s, keeps its whole output (a JSON document cut at its head does not parse), runs through `CliRunner` (so it is in Activity) and is parsed on the pool. `InstallationGate.IsKnownRead` calls the whole shape a read, as it does the redaction and policy reads, so on a managed installation the lists are still read. `CommandTiers.Classify` still says "change" for them (the first recognised verb, `setup`, decides; extending its named exceptions would move the pinned read-only sets of both runtimes' command trees, which this issue does not need); Activity's footer (section 14) therefore asks the guard instead of the classifier before it claims "config reloaded", so a list that was only looked at does not claim it. The Rerun of such an entry still opens a review, at the classifier's tier.
- **Empty is not failed.** A read that printed `[]` is the Empty state; nothing printed, a non-zero exit, a timeout, output that is not the list, and a missing CLI are each their own failed state, with the reason. The CLI always prints `[]` for an empty list, so empty output is never taken for one. A refresh that fails keeps the rows on screen under a bar that says they are from an older read, and turns every change off (`CatalogTrust`: the same rule as section 9, including config.yaml and .env changing under the list). The trusted-folder editor says "Could not read the trusted-path allow-list" and "this is not an empty list" (the TUI's error row), since the built-in folders always fill a working one.
- **One reason, the installation first (section 10).** `BlockedReason(verb)`: the installation's sentence, then the list's trust (not read, failed, older, config.yaml changed), then another command running, then no row selected, then the row's own reason (a built-in is protected; a destination the compiler generates is not in config.yaml, so it cannot be enabled, disabled or removed; a destination in the state asked for, one that belongs to a local stack this PC cannot run, and a local destination Test cannot reach all say so). A control that is off carries its reason as its tooltip, also while disabled, and a review confirmed after the installation or the list changed runs nothing and records one refusal (`RunGuard`, `CliRunner.RecordRefusal`). Add needs only the installation: the wizard shows its own command. The hub's three tiles stay on for a read-only installation (their window only reads there; every other tile is off) and say "Changes are off" with the sentence.
- **No address is shown whole.** `EndpointHost` builds on `EndpointDisplay` (section 13): every row's endpoint is `EndpointDisplay.Host` of what the CLI printed (`https://hooks.example.test/***` already has its path replaced by `redact_webhook_url`; a destination's `redact_endpoint_for_display` keeps the path, and so a token in it is cut here), a local destination keeps its path text, and an address that cannot be vouched for is `<unreadable endpoint>`. **`setup webhook test` prints the webhook's address whole** on its first line, and a chat webhook's secret is its path, so every run of these editors carries `CliRunOptions.OutputLineFilter = EndpointHost.ScrubLine` (new): the runner applies it to each line after the known-secret scrub and before the line is stored or streamed, so Activity, the review's result, the clipboard and the notice hold `scheme://host[:port]` only. It fails closed (a filter that throws replaces the line with a fixed notice) and leaves the rest of a line as it was, indentation included, which `EndpointDisplay.ScrubText` (trims and cuts) would not.
- **Trusted folders.** Columns are the TUI's Source, Status, Owned and Path. Built-in folders (`source: default`) have no Remove, nor has an entry only the running process's environment names or any the CLI marks not removable; the button says why. The folder is checked with `ArgvHazards` before a review is offered (the CLI expands `%VAR%`, `$VAR`, `~` and wildcards in every argument on Windows, so a folder that would be rewritten is refused). A card lists the connectors whose program sits in a folder that is not trusted, which the TUI computes by running discovery in-process: the app has no read-only scan, so it reads `agent_discovery.json` (what the last scan left, bounded at 1 MiB, off the UI thread), says when that scan was, leaves out a folder already in the list in good order, and says "no scan recorded" or "could not be read" when that is the case. Trust on a connector opens the Add wizard on `add` with its folder typed in. A folder is only suggested when it is an absolute path with no leading dash and no control or direction character (`TrustedFolders.IsOffered`).
- **Prefill from a failed connector setup.** The TUI checks the last discovery scan before it starts a connector setup and opens the editor with the folder and a sentence (`_route_untrusted_binary_to_panel`). The app has no read-only scan to check with, so it offers the same step after the run: a setup that cannot probe its connector's program prints `Trust it with: defenseclaw setup trusted-paths add <folder>` (`cmd_setup._emit_untrusted_prefix_setup_hints`), and when a run exits non-zero having printed it the wizard's result bar says so and offers **Trust this folder...** (`TrustHint`, `WizardViewModel.TrustFolderCommand`), which opens the editor with the folder on a banner and its own Trust button. Nothing is trusted from the wizard: the editor's Add opens the add wizard, which ends on its own review. `WizardLauncher` wires the button; the view-model never opens a window.
- **Not claimed.** The editors were written against the installed 0.8.10 CLI's source and `--help`; the pinned runtime's copy of these commands was not compared. `setup webhook list` lists the global webhooks only (the per-connector lists under `observability.connectors` are not here). The trusted-folder editor does not run discovery, so the connectors card is as old as the last scan.

## 17. The status strip's chips - `StatusStripViewModel` / `ChipStripPanel` / `StatusFacts` (CUST-273)

**For:** the TUI's `widgets/status_strip.py` shows more than a gateway pill, a connector, the alerts and a version. The strip between the state pill and the buttons now has its chips: **Watchdog, Guardrail, Keys, Alerts, Connector, Redaction, Policy, Running, Stale, Version**, and a `+N` chip for the ones a narrow window has no room for. The shell view-model owns it as `Strip` (`MainWindowViewModel.Strip`); the view is `StatusStripControl`, which takes the star column of the strip row and holds the gateway's detail sentence and the chips.

| Chip | Says | Tone | Comes from |
|---|---|---|---|
| Watchdog | `Watchdog` while it runs, `Watchdog: stopped` otherwise | the Overview Services card's | `/health` `watcher`, through `OverviewPanelViewModel.BuildServiceCards` (the same words and tones as the Services box) |
| Guardrail | `Guardrail`, or `Guardrail: disabled` | the Services card's | `/health` `guardrail`: the live state only, never a missing credential laid over it |
| Keys | `Keys: missing A, B (+N more)` (the TUI's wording) | Bad | `StatusFacts.MissingKeys`, handed over by the Credentials card (CUST-266) after `keys list --json`; names only |
| Alerts | `3 recent alerts · 1 critical` | Critical when one is | as it always was (`GatewayPresentation`) |
| Connector | `Connector: claudecode`, `No connector`; with several `All connectors (3)` or `codex (filtered)` | neutral | the snapshot's roster and `ConnectorScope.Current` |
| Redaction | `Redaction: per-route · unredacted` | **Warn** when events leave unredacted (the label says so, or lists `none` among the profiles), Ok when routes redact, neutral while loading / unavailable | `StatusFacts.Redaction`: the Overview's aggregate label (`ObservabilityPlan.RedactionSummary`), as it is |
| Policy | `Policy: observe` / `Policy: action` | neutral | `/health` `guardrail.details.policy_mode` (the Overview's Guardrail tile's order), else config.yaml's mode for the connector in scope; says which in its tooltip |
| Running | `Running`, `Running 3` | in progress | `CommandActivity`: any command in flight on `CliRunner` (not only scans, which is `ScanActivity`'s); a hand-off or a refusal is born finished and never counts |
| Stale | `Stale` | Warn | the monitor's last good poll is more than 3 polling intervals old (below) |
| Version | `DefenseClaw 0.8.10` | neutral | as it always was |

- **Nothing here reads anything.** Every chip is derived from state that exists for another reason. The two things a panel read for itself - the credentials still missing (Setup) and the redaction label (Overview) - cross to the strip through `Services.StatusFacts`: a panel *publishes* what it read (`CredentialsViewModel.ApplyRows`, `OverviewPanelViewModel.BuildObservability`), the strip subscribes. Panels are built on their first visit and idle while hidden, so the strip cannot ask them, and must not ask the CLI. **A fact nobody has handed over is `null`, not "none"**: the chip is not drawn (Keys appears once Setup has read the list; Redaction once the Overview has built its card, which is the landing page). A read that fails publishes nothing, so the last good list stands and a failure never reads as "all clear".
- **Words and tones are the TUI's** where it has them; `StripPresentation` holds every rule as a pure function. Colour is never the only cue: a subsystem that is not running says its state in words (`Guardrail: error`), every chip has a tooltip and a UI Automation name that says the whole fact, and the text inside a chip is a `StripText` that UI Automation leaves out, so each chip is read once. A chip is one element for a screen reader: name = the sentence, help = the tooltip. While monitoring is paused the Watchdog and Guardrail chips are neutral and say they are the last reading.
- **The monitor's snapshot now notices the two subsystems.** `/health` as a whole is not compared by `RendersSameAs` (uptime and counters move on every poll), so a guardrail that turned from running to error would have left an always-alive strip on the old reading. `GatewaySnapshot.SubsystemReading` (the two states and last errors, the policy mode and the enforcement flag) is part of the compared set; a poll that differs in nothing else still raises nothing.
- **Stale** (`PollFreshness`, `IPollFreshness`): on while `now - last good poll > 3 x the polling interval` (strictly more), where the interval is what the monitor waits now (`GatewayMonitor.Cadence`: the Settings page's health pulse, or the 30 s slow lane after repeated unreachable polls) and the poll's age is on the **monotonic clock** (`GatewayMonitor.SinceLastGoodPoll`; a wall-clock step cannot make data look old). A *good* poll is one that finished without a fault: a poll that throws (even after the monitor surfaces it as "The gateway poll is failing", which is stamped with its own time) and one that never returns bring nothing. Nothing is stale before a first good poll (the pill says "Checking…") or while monitoring is paused (the pill says so). A monitor whose poll is blocked publishes nothing, so no event can say it: while the strip is on screen (`StatusStripViewModel.SetActive`, driven by `MainWindow.PublishInteractivity`) it looks again every polling interval (`PollFreshness.LookEvery`: the interval, bounded to 1-10 s) - a comparison of two numbers on a `TimeProvider` timer - so the chip is on within one interval of the line being crossed. It looks again at once when the strip comes back on screen, when a snapshot arrives and when the health pulse or the pause changes; **off screen it keeps no timer.**
- **Collapse** (`ChipStripPanel`, arithmetic in `ChipStripLayout`): lowest priority goes first, in the issue's order - gateway (the pill: never), guardrail, **watchdog**, keys, alerts, connector, redaction, policy, **running**, stale, version (the two in bold are not in the issue's list; the watchdog goes with the guardrail, a command running is transient and goes with the other short-lived ones). The detail sentence trims first, down to 100 DIPs, then chips are hidden one at a time, highest number first, until the rest fits (ties: the later one); the `+N` chip's room is counted before deciding, so showing it never pushes another chip out. The result is monotone: a wider window never hides more. A hidden chip is **not** collapsed - it is arranged with no room and clipped, so the panel can measure every chip at full width on every pass (a collapsed chip cannot be measured, and a layout built on collapsing flips chips in and out as it guesses their width) - and is marked off screen for UI Automation; the `+N` chip lists what is hidden in its tooltip and name, **in the tone of the worst of them**, so a Redaction warning or a missing key with no room still colours something.
- **Known limits.** A Keys chip with two long names is ~370 DIPs wide (`CISCO_AI_DEFENSE_API_KEY`) and, being second only to the subsystems, outranks the alerts: in a narrow window it goes into `+N` - in red - together with everything below it, because the order is strict and a chip has no compact form. The Keys chip draws only once Setup has read the list, and the Redaction chip once the Overview has built its card (see above): the strip never reads for them.
- **The look is the design system's**: `DcBadge` / `DcChip` by `Tag`, `DcStatusGlyph` on the subsystems, 12 px text (the chips used to be 11), every colour a token.
- **What was removed**: `MainWindow.UpdateStripDensity` and its thresholds (the version chip below 1040 DIPs, the connector chip below 900, widened by `DetailSentenceExtra` for a monospace look) are replaced by measuring the chips in the font on screen; `StripDensityTests` went with them, and the same promises (no overflow at the minimum width under every look, the sentence not squeezed out) are `StatusStripLayoutTests`.
- **Not in the strip**: the TUI's `N cmds` counter and `unfocused` chip (the issue does not list them).
- **Tests.** `StatusStripChipTests` (each chip's mapping, tooltip, name), `StatusStripStaleTests` (the acceptance: a blocked poll on a real monitor and a clock the test moves; the look's cadence; no timer off screen), `ChipStripLayoutTests` (the arithmetic, with a seeded fuzz of its invariants), `StatusStripLayoutTests` (the real panel, fonts and looks at 400-1600 DIPs on the UI thread; UI Automation; `DC_RENDER_DIR` writes PNGs), `StatusFactsTests`, `StatusStripShellTests`, `StatusStripWindowTests` (the real `MainWindow`, never shown: the strip's data context, and nothing left subscribed once it closes), `StripPresentationTests` (the wording rules as pure functions), `CommandActivityTests`.

## 18. "New since last visit" on the sidebar - `UnreadCountsService` / `AuditHeadReader` / `SeenSettings` (CUST-265)

**For:** the 0.8.10 TUI's tab strip says `Audit (7)` when a stream panel has more in it than it had when the operator last opened it (`tui_state.py` `panel_seen_counts`, `app.py` `_panel_unread_count`: `max(0, total - seen)`, capped at 99, not shown on the active panel). The sidebar does the same for **Audit, Activity and AI Discovery**: an accent capsule ("7", "99+") whose accessible name is "Audit, 7 new since last visit".

```csharp
Services.UnreadCounts.Changed += (_, e) => Capsule = UnreadPresentation.StateOf(e.Counts["audit"]);   // UI thread; subscribing starts it (while the window can be seen)
Services.UnreadCounts.PanelShown("audit"); Services.UnreadCounts.PanelLeft("audit");               // PanelCatalog calls these on every activation change
Services.UnreadCounts.ReportAiDiscovery(AiDiscoveryNovelty.Parse(stateFileText));                 // a reader that already holds ai_discovery_state.json
```

- **A position, not a count.** The TUI remembers *how many* items a panel had and compares that with the length of its list. That stops working when the list is capped (its Audit list is the newest 500, so on a real database the tab never lights), trimmed or cleared, and its AI Discovery count reads `snapshot.agents` on an `AIUsageSnapshot` that has no such member, so it is always 0 on 0.8.10. `AppSettings.Seen` (`seen` in settings.json, `SeenSettings`) keeps where the operator looked, per panel id: the newest `rowid` of `audit_events` for Audit, a UTC instant (ticks) for Activity (when its runs started) and AI Discovery (when a component was *first seen*). Absent is "never looked", which is not 0 (an empty table that was looked at). Ids are bounded, values are never negative, 32 panels at most, and a member this build does not track survives a write.
- **When it moves.** When the panel is shown *and* when it is left (the issue's wording; the TUI moves it only on arrival, so what scrolled past while the panel was open comes back as "new" the moment it is left). The window going to the tray leaves the panel on screen, so it moves then too. A visit's marker is written from a pool thread, coalesced, and only when it changed; the Settings page ignores `Seen`-only changes (a half-typed path is not wiped by a sidebar count).
- **Audit** (`AuditHeadReader`): nothing reads `audit.db` while its panel is off screen, so this is the one count that costs a statement. It rides the monitor's 30 s alert tick (`AlertCadenceElapsed`, the one the alert counts use) and asks the shared `AuditChangeProbe` first: **unchanged is one `PRAGMA data_version` and no statement**; changed is one statement of two index probes (`MAX(rowid)` and `COUNT(*)` over `rowid > $marker LIMIT 100`, plan pinned: a search on the rowid, never a scan; no row text is read), at most once per tick. Measured read-only on a live database (tens of thousands of rows, newest rowid in the hundreds of thousands: retention deletes old rows and rowids do not restart): 14-20 µs warm whatever the marker's distance (p95 under 50 µs, the slowest of 1,000 runs 2.9 ms), against 3 µs for a `data_version` sample. The marker is a rowid, not a time, because the gateway commits some rows late (5% of a real database, up to ~2 minutes behind a newer one; the live refresh's `LateCommitWindow`): a timestamp marker would never count them. A head *below* the marker (the table was emptied, or `VACUUM` renumbered it) starts again from the head instead of counting a renumbered table as new. The panel on screen is not counted or read (it shows its own rows, live). A read that fails keeps the last count; it never zeroes the badge. A show or a leave reads the head once (memoized by the probe, so none when the database did not move): user-initiated, at the moment the Audit panel reads far more itself.
- **Activity**: the runner's in-memory list (`CliRunner.Activity`, at most its capacity) counted past the marker; no I/O, recounted when a run starts (`InvocationStarted`, an event that exists anyway) and on the tick. With no marker everything in the list is new (it is this session's own).
- **AI Discovery**: a reader that already has the state file's text hands over when each component was first seen (`AiDiscoveryNovelty.Parse`: a product per vendor and product, a local model per model id, the earliest known `first_seen`): the **Overview's agents card**, on its slow cadence, which is therefore also what refreshes this count while the Overview is on screen. Nothing is read for it, so it is as fresh as the last time the Overview read the file and says nothing before that. The scanner's own `state: new` is *not* used: it lasts one scan. What the AI Discovery panel shows is what has been seen: it tells the service when its data was read (`NoteAiDiscoveryDisplayed`) and the marker follows that while the panel is on screen, so something found after its last load is still new when it is left.
- **First sight.** A panel with no marker gets one at its first look (Audit's head, AI Discovery's file) instead of having its whole history called new: a first launch shows no capsule anywhere.
- **Presentation.** Capped at 99 (`UnreadCountsService.Cap`; the count goes to 100 so "more than 99" is known without counting on): the capsule reads "99+", the sentence "99+ new since last visit". Hidden on the panel on screen and while a visit is still moving its marker (no "2 new" flashed for rows the operator has just seen). The capsule is `InfoBadgeSeverity.Attention`, the style's accent (the alert count stays red, the Overview's gateway mark amber); its text is 4.5:1 or better on its fill in every style and mode but Linear Light (4.1:1: the style's own tone tokens; its red and amber capsules measure 4.4 and 4.0 there). `MainWindowViewModel.UnreadBadges` / `UnreadFor(panelId)` carry it; `MainWindow` keeps one `SidebarBadge` per tracked panel.
- **Idle costs nothing.** No timer, thread or watcher of its own (a test fixes the types of its fields). It is attached to the alert tick and the runner's start event only while something listens to `Changed` (the dashboard window's view-model, for as long as the window lives) **and** the window can be seen (`SetInteractive`, fed by `PanelCatalog.SetWindowInteractive`: not in the tray, not minimized); coming back reads once. Hidden to the tray, with monitoring paused (no tick), or with no window, it does no work at all. Counted, not timed (`UnreadIdleCostTests`): twelve ticks on an unchanged database are twelve probe samples and no statement; a commit makes exactly the next tick run one statement; a tick adds nothing to the counters of the readers the rest of the app runs (the Audit panel's page and count queries, the alert queue); Activity costs no read of any kind; a tick that finds a pass still running is skipped, not queued.
- **Logs is not tracked, on purpose.** `gateway.log` and `watchdog.log` lines carry no id or time (the 0.8.x sidecar writes bare lines), so there is no marker that survives a restart or a rotation; nothing reads either file until the Logs panel has been opened once, and then the tails only buffer; the Verdicts and Events streams are audit rows the Audit count already includes. An honest number would need a read the app does not make today, and a session-long counter of routine gateway chatter would sit at 99+. Adding a panel later is one id in `UnreadCountsService.TrackedPanels` plus a source.
- **Tests.** Core: `AuditHeadReaderTests` (head, bounded count, late commit, retention, renumbering, no database, memo, plan, read-only). App: `SeenSettingsTests` (round trip through a second store, tolerance, the Settings page), `UnreadPresentationTests`, `AiDiscoveryNoveltyTests`, `UnreadCountsServiceTests` (per panel over fixtures: cap, hidden on the active panel, markers moving on show and leave, restart, reset, failure keeps the count), `UnreadIdleCostTests` (the counters above), `UnreadViewModelTests`, `PanelCatalogUnreadTests`, `OverviewAiDiscoveryFeedTests`, `UnreadCapsuleViewTests` (capsule, name, tooltip, live style switch, contrast) and `UnreadSidebarWindowTests` (the real dashboard window, off screen: a new audit row raises the Audit entry's capsule, opening the panel clears it, the tray detaches the counts).

## 19. Logs presets, the event detail, the pause count and the keys - `LogSignalRule` / `EventDetail` (CUST-263)

**For:** the parts of the 0.8.10 TUI's Logs panel (`tui/panels/logs.py`, `tui/services/gateway_log_views.py`) the Windows panel only approximated: what the default "No Noise" view hides, what Errors / Warnings+ / Scan / Drift / Guardrail keep, the labelled fields of a verdict or an event in the detail, and three small controls (the count of what arrived while paused, `e` / `w`, `g` / `G`).

```csharp
LogSignalRule.IsNoise(line); LogSignalRule.HasActionableSignal(line);   // the TUI's NOISE / ACTIONABLE / LOW_SIGNAL tables, one question each
ActionableRule.ContainsAny(text, patterns);                              // the matcher the Logs rule and the Audit / Alerts rule share
LogPresets.Matches("no-noise", entry, hideLowSignal: !isEvents);         // the preset rules over LogEntry.MatchText (the line the TUI would match)
streamEvent.Detail.Rows(severity);                                       // Stage, Direction, Model, Provider, Request ID ... Finding 1, Finding 2
```

- **No Noise is the Logs rule, not `ActionableRule`.** Both are the TUI's "a row is quiet only if it is marked quiet and says nothing actionable", but over different inputs and different lists. The Audit / Alerts rule (§12) reads a severity *column* (an exact set of low-signal levels) plus a haystack and 13 words (`AUDIT_ACTIONABLE_TOKENS`). The Logs rule reads one rendered *line* in which the severity is a word, with `NOISE_PATTERNS` (6 heartbeats), `ACTIONABLE_LOG_PATTERNS` (18: the 13 words, `warn`, `critical`, `" high "`, `severity=high`, `severity:high`) and `LOW_SIGNAL_LOG_PATTERNS` (9: `" info "`, `" low "`, `" medium "` and the `severity=` / `severity:` forms). The lists differ (a WARNING row that only says "warn" is signal to Logs and low-signal to Audit / Alerts), so they stay two tables, as upstream keeps them, in `LogSignalRule` beside `ActionableRule`; what they share is the matcher (`ActionableRule.ContainsAny`: a case-insensitive substring over a list), so they can differ in a list and never in how a list is read. `LogSignalRuleTests` holds each table to a verbatim copy of the TUI's and the Logs list to its relation with the Audit one (every Audit word is a Logs signal word; five more).
- **What the rule reads.** A log-file line as it is. An event as the line the TUI renders: `LogEntry.MatchText` is the severity as a word padded with spaces (`" info     "`; `INFO` when the row has none, as the TUI's `_upper_or`), then the bucket, the message and the target - which is what lets `" info "` and `" high "` mean something for an event. `LogEntry.IsNoise` and its six strings are gone; "event sessions.changed" is now the TUI's `event sessions.changed seq=nil` (with a real sequence number it is no longer dropped).
- **Where it applies.** Gateway, Watchdog and Verdicts: the whole rule. **Events: the heartbeat half only** (`hideLowSignal: false`). The low-signal rows of Events are the "Actionable only" switch's (§12), whose promise - turn it off to see every event - the preset would otherwise break (the default preset is No Noise); with the switch on, Audit / Alerts' rule narrows the stream, as before. A consequence worth knowing: **Verdicts now open without the quiet rows** (an INFO allow that says nothing actionable), as the TUI's do; preset `all` shows them, and the empty state says so.
- **Errors and Warnings+** keep the Mac's severity floor (High, Medium) and add the TUI's words wherever the row says them: `error`, `fatal`, `panic` (and `warn` for Warnings+). That is what puts an event stored with the severity `ERROR` (not on `AuditSeverity`'s ladder, so `Unknown`) in Errors, as it is in the TUI, where the word is in the line's severity column. `panic` is also an error on the tone bar (High, with `error`; `fatal` stays Critical).
- **`http 4xx` / `http 5xx` stays** in Errors and Warnings+ (and on the tone bar and above a severity floor), where it was the app's own addition: the TUI colours and filters on `error`, `fatal` and `panic` only, so a bare `HTTP 503` line is not an error there. Kept because a refused or failed request is what an operator filtering for errors wants, the tone bar and the severity picker have always agreed with the presets about it (`LogsStreamsTests` pins the severity), and a false positive costs a row where a miss costs the failure. It is the one place these presets show more than the TUI's; `LogPresetsTuiTests` holds both facts (the TUI's three words do not include it; the preset does).
- **Keywords.** Scan also keeps `finding`, Drift `rescan`, Guardrail `guard` (the TUI's; the Mac's `verdict` / `judge` stay). One list per preset in `LogPresets`, tried against every word in `LogPresetsTuiTests`.
- **The detail of a verdict or an event** (`EventDetail`, `StreamEvent.Detail`; the inspector's grid, `LogEntry.Fields`) is the TUI's `detail_pairs` under its labels and in its order, each row only when it has a value: Timestamp, Event type, Severity, Action; Stage, Direction, Model, Provider, Request ID, Run ID, Trace ID, Span ID, Session ID, Categories, Latency (ms), Judge kind, Reason, Judge severity (only when it is not the row's), Judge input bytes, Judge parse error, Finding 1..N; then what the app adds - Bucket and Event name (the TUI's Subsystem and Transition), a hook call's labelled rows (`StructuredDetailParser.InspectorRows` over its details, for a row whose action is `connector-hook`; they carry the Connector), Error code, Connector, Target, Actor, ID. The heading says "Event details" (a file line's stays "Line details" and its fields are unchanged). The TUI prints its blank rows and, because its projection fills them for every row, "Error ..." and "Diagnostic ..." rows on rows that are neither; those are not reproduced.
- **Where each field comes from** (the TUI's keys, `_v8_gateway_log_row`): Stage the last part of the event name; Direction `gen_ai.operation.name` else `defenseclaw.hook.event`; Model `gen_ai.request.model` else `gen_ai.response.model`; Provider the row's `source`; the four ids the row's own columns (`run_id`, `trace_id`, `request_id`, `session_id`); Categories `defenseclaw.guardrail.rule_ids`; Latency `defenseclaw.guardrail.latency_ms` and, where that is absent, the judge's own `defenseclaw.judge.latency_ms` (the TUI does not read it, and a judge event has no other); the judge's kind, input size and parse error `defenseclaw.judge.kind` / `.input_bytes` / `.parse_error`; Reason the same summary the row's message uses. Everything is masked (`DisplayRedaction`) as it is read.
- **Judge findings and a judge's severity come from keys nothing registers.** The TUI's detail has a "Finding N" row per finding and a "Judge severity" row, but its canonical projection never fills the finding list and sets the severity to the row's own, and the pinned catalogue's judge log (`guardrail.judge.completed`) carries only kind, action, latency, input size, parse error and error summary. So a database written by either runtime today shows neither. They are read from `defenseclaw.judge.findings` (an array of `{category, severity, rule, source, confidence}`, the gateway's own `Finding` shape) and `defenseclaw.judge.severity` when a payload has them, and shown as the TUI's detail would: `Finding 1: category=... severity=... rule=... source=... conf=0.90`. A list is cut to 32 entries.
- **The span id** is in the stored record (`projected_record_json`, `correlation.span_id`), not in a column. A second statement - by id, 400 at a time, `json_valid` and `json_extract` inside SQLite, only for a record within the 64 KiB limit - fills it in for the rows a read has just projected, so a poll over a quiet database, or over rows already seen, parses no record (and the six arms of the Verdicts statement never do). On a synthetic 30,000-row database with 1.3 KB records a cold read of 1,000 rows cost about 15-50 ms more (the noise of the machine included); a read that finds nothing new costs nothing. A build without the JSON functions leaves the span id empty and reads the stream all the same; any other failure is the read's.
- **An oversized payload is unavailable, not empty** (CUST-284): the fields that live in it are not shown and the inspector adds an `Unavailable` row (`payload_json is 70 KB, over the 64 KB limit`); the row's columns - the ids, the severity, the details - still are.
- **"+N since pause"** is in the status line (`12 shown · 12 matching · 40 total · +5 since pause`) while "live" is off, `+0` included. The TUI's hint bar says "New lines since pause: +N" and counts the growth of the source's line list; here it counts arrivals, so a full 5,000-line buffer still counts. Like the TUI's it is what the source received, before the filters (heartbeat lines the preset hides count). A log file counts the lines its tail delivers; Verdicts and Events count the rows a poll found that the one before did not - not the first read, and not what lands while another stream is on screen, since they are read only while shown. Every stream takes its baseline at the moment of the pause, so switching stream while paused counts from then; resuming forgets them.
- **E, W, Home and End.** `e` / `w` are the TUI's: each toggles its preset against **All** (not against the one before it). Bare keys, as in the TUI, handled by the panel (`LogsPanel.OnKeyDown`) only with no modifier and not while keyboard focus - or the key's origin - is a text box, a password box or a combo box (a closed combo box jumps to the item that starts with the letter, so `E` would pick "errors" twice). They collide with no chord: every shell chord has Ctrl or is F1 / F5 / Esc (`ShellShortcuts.ShellChords`), Ctrl+E is Audit's export and Ctrl+Shift+E the shell's export of the last output, neither of which the bare-key test sees (`ShellShortcuts.IsLogsErrorsKey` and its three siblings, held by `LogsPauseAndKeysTests`). They are in the Keys overlay under "Inside a panel". Home / End in the list are the TUI's `g` / `G`: Home selects the first row and **pauses**, End selects the newest and **resumes**, and the list scrolls to it and takes focus there; with Shift or Ctrl they stay the list's own. Selecting a row opens its inspector, as the arrow keys do.
- **Not done.** The TUI's `line_style_key` (dimmed noise, green connected lines); Verdicts' action / type / severity chips (the app has the pickers); the judge response modal's own labels (CUST-260); the per-type lines the TUI renders for the Verdicts stream (the app shows one list shape for both streams).
- **Tests.** Core: `LogSignalRuleTests` (the three tables against verbatim copies of the TUI's, every pattern tried, the relation to the Audit rule, the shared matcher), `EventDetailTests` (the list against the TUI's labels and order, the payload keys and their fallbacks, ids, span lookup including chunking and bad records, masking, bounds, hook and error rows). App: `LogPresetsTuiTests` (every preset against every pattern of the TUI's lists, for lines and for events; the `http` decision), `LogsInspectorFieldsTests` (a synthetic judge event with findings through the real reader and panel shows every label in the TUI's order), `LogsNoNoisePanelTests` (the default preset through the panel: files and Verdicts get the whole rule, Events the heartbeat half, the empty state), `LogsPauseAndKeysTests` (the pause count, E / W / Home / End at the view-model, the collision tests, the overlay), `LogsKeysViewTests` (the keys through the real view, the inspector of a judge event, and its PNG when `DC_RENDER_DIR` is set).

## 20. The pending-restart queue - `RestartQueue` (CUST-267)

**For:** "a change is saved and the running gateway does not have it yet". The gateway reads `config.yaml` when it starts, so a config-editor save, or a wizard, guardrail or discovery run told `--no-restart`, is not in effect until it restarts. The TUI keeps a queue of the reasons on its Setup page (`tui/services/setup_state.py: RestartQueue`: reason, queued_at, last_started_at, with `[G] restart now` and `[C] clear`) and shows it as the readiness checklist's "Restart Pending" row; this is the same queue, app-wide: the Setup hub's banner, that row and an Overview attention row all read it, "Restart now" and "Clear" are on the banner and the row, and a restart by any route clears it.

```csharp
Services.RestartQueue.Queue("config.yaml saved in the config editor (llm)");   // a line and its queued-at time (a blank reason queues nothing)
Services.RestartQueue.IsPending / .Reason / .QueuedAt / .Entries               // the TUI's pending / reason ("a; b") / queued_at, and each line's own time
Services.RestartQueue.Clear();                                                  // the operator's Clear
Services.RestartQueue.Changed += (_, _) => Redraw();                            // UI thread; a panel subscribes only while it is on screen
RestartQueueReview.Open(Review, Services)                                       // Restart now: the reviewed `defenseclaw-gateway restart`
```

- **What queues.** Two inputs, and no call at the place that runs a command. (1) The config editor, after a save that changed a value (`RestartQueueRules.ConfigSaveReason`: the two texts are parsed and compared, so a comment, spacing, blank lines, key order, a flow list written as a block one or the quote style of a string that stays a string is the file and not what the gateway reads; a plain value that became a quoted one counts, as `true` and `"true"` are a bool and a string; the reason names the top-level sections that differ and never a value, and a text that does not parse is called changed). A rejected save queues nothing, nor does one the installation refused; a restore from a backup queues a line unless it replaced a file our own save wrote and the CLI rejected (the usual reason to restore: the file goes back to what the gateway has). The editor's own transient bar ("Saved - restart the gateway to apply") is unchanged beside it. (2) **The runner.** `RestartQueue` listens to `CliRunner.InvocationCompleted`, so a wizard, the Setup guardrail buttons, the Guardrail controls window, AI Discovery's enable / disable, the Runtime panel, the first-run plan, the palette and a Rerun all queue without calling the queue themselves (`WizardViewModel` needed no edit). A finished run queues `<command words> ran with --no-restart` (`RestartQueueRules.PendingReasonFor`) when it succeeded, ran `defenseclaw` with a standalone `--no-restart`, is not a read or a preview (`InstallationGate.IsReadOnly`, the runner's own word) and - for the `setup` and `guardrail` verbs - **`CommandReview.RestartsGatewayFor` says it would have restarted the gateway without the flag**. That is the review's rule, asked of the command less its flag, not a second one; for a verb it has no opinion on (`agent discovery enable | disable`, `agent discovery runtime enable | disable`) the flag is the evidence, since the CLI exits non-zero on an option it does not know. The words are the TUI's label for the command (`CommandNextAction.LabelFor`: `guardrail hilt`, `setup claudecode`, `agent discovery`), never an argument after `--` or a typed value. A run the rule calls a restart (`setup local-observability up`, which restarts through the `setup` group's callback and has no such flag) clears instead.
- **What clears it, by any route.** Seen from the gateway, with no timer of its own: each poll the monitor completes carries the start time `/health` reports (`started_at`, else the poll's time less `uptime_ms`; a start before 2000, ahead of the poll, or an uptime of centuries is not believed), and a start **at or after the moment a line was queued** applies that line - the gateway read `config.yaml` when it started - so the tray, the palette, Restart now, another app and a terminal all clear it, line by line. A different `binary_version` than the one running when the queue began applies everything (an upgrade). Seen from this app's own runs: a command `CommandOutcome` calls "gateway restarted" (exit 0 and `RestartsGatewayFor`, or `defenseclaw-gateway restart`) applies the lines queued before it began, without waiting a poll; a line queued while it ran is left to the poll. `defenseclaw-gateway start` is not a restart; a gateway that was down and comes up is a new start time. And Clear: it forgets the queue without restarting (what was saved stays saved, and applies at the next restart).
- **Why `last_started_at` is not stored.** The TUI compares the gateway's start with the one it saw when the line was queued. That baseline is the monitor's last poll, up to one interval old, so a restart just before a save would be seen by the next poll as "the gateway restarted" and clear a line the restart never read: a change taken for applied, silently. Comparing the start with each line's own queued-at has no baseline to go stale, and its failure is the safe one - a banner that stays until Clear. (The TUI's own auto-clear never fires for what it queues: `queue_restart` is called only by the Setup config save and never with `last_started_at`, so `should_clear_for_started_at` is always false; what clears its queue is `[C]` and any successful `defenseclaw setup ...` run, even one run with `--no-restart`. The queue here follows the intent in the issue and in the Go TUI's comment, not that quirk.) A line queued again (the same reason) is one line with the later time, for the same reason.
- **Not persisted - the TUI decides.** `SetupPanelModel.restart_queue` is created empty in the model's constructor and written nowhere, so it does not survive the TUI; this queue lives as long as the app process (a tray app: across panel switches, and closing the window to the tray) and is empty at the next start. A restart pending when the app is closed is forgotten, as in the TUI.
- **No timer.** The queue listens to `GatewayMonitor.PollCompleted` (`IGatewaySnapshotSource` gained it; the monitor already had the event) **only while a line is queued**: with nothing queued the poll costs the queue nothing and the monitor queues no delivery for it (`PollCompletedSubscriberCount`). It listens to the runner for the life of the process (one comparison per finished command). `Changed` is raised on the UI thread, each handler on its own; every reader is safe on any thread. At most 20 lines are kept (the oldest goes), each at most 200 characters on one line.
- **Where it shows.** Setup hub: a bar at the top of the page (`SetupPanel.xaml`, built like the update banner: tokens only, the Medium tone, a polite live region) with the reasons, when the first was queued (a time, not "3 minutes ago": nothing ticks) and what a queued restart means, **Restart now...** and **Clear** (`SetupPanelViewModel.Restart.cs`; it follows the queue only while the panel is on screen and reads it when it returns, so it is right after any number of panel switches). Readiness: the "Restart Pending" row is the TUI's - `warn`, the reasons joined with `; ` as its detail, the reviewed restart as its Fix - fed from the queue (`ReadinessViewModel.QueueRestart` is gone; CUST-266's row was queued only by the Setup guardrail buttons). Overview: a Medium "Gateway restart pending" row right after the gateway's own rows, with the same two buttons in the row (`OverviewPanelViewModel.Restart.cs`, `AttentionRow.OffersRestart`).
- **Restart now** is the reviewed `defenseclaw-gateway restart` the tray, the palette and the Overview's gateway button already run (`RestartQueueReview.Open`): the exact argv `GatewayControl.Argv(Restart)` on `defenseclaw-gateway` - never a bare `defenseclaw-gateway`, which would start a second daemon - through `DiscoverActionReview`, so it is in Activity and the review states the restart. **Off with the installation's sentence first** (`GatewayControl.Availability(..., Services.Installation)`: managed or invalid, then "still checking the gateway", not installed, not initialized), also while a line is queued; reached anyway (a keyboard route, a button drawn before the flip) it opens nothing. A review opened while the installation was writable and confirmed after it turned read-only runs nothing and records one refusal in Activity (`DiscoverActionReview`, `CliRunner.RecordRefusal`: CUST-308 and CUST-312's, unchanged). Clear is the app's own list, not a change to DefenseClaw, and stays on. Once the run finishes the monitor is polled so the shell follows.
- **Not claimed.** A change saved from the TUI or a terminal is invisible to the app, so it queues nothing; the pinned runtime reports `config.details.restart_required` in `/health`, which is not read (it would be a newer-runtime feature behind a capability gate). Whether a particular setting needs a restart is not known: every value changed in `config.yaml` queues, as every saved diff does in the TUI.
- **Tests.** `PendingRestart\RestartQueueRulesTests` (what queues and what does not, as tables; the config comparison; the gateway's start time), `RestartQueueTests` (lines, auto-clear on a start-time change and a binary version over a fake monitor, a finished restart, Clear, nothing subscribed while empty, the runner's own finished command through a real child, the composition's wiring), `RestartQueueSurfacesTests` (Setup, the readiness row, Overview, across panel switches, Restart now guarded and refused), `RestartQueueViewTests` (the banner and the row, in both panels, rendered), `ConfigEditor\ConfigEditorRestartQueueTests`.

## 22. Multi-command Setup flows - `SetupPlan` / `NotificationRouting` / `AiDiscoveryTuning` / `ConnectorBatch` / `SetupStateLines` (CUST-271)

**For:** the TUI's multi-step setup flows (`SetupCommandIntent.follow_up`: Notifications Routing, the connector picker, the AI Discovery wizard) and the Mac's multi-command wizards. Three dialogs on the Setup hub and the AI Discovery panel, each ending in **one review** of the exact commands, and a line of current state on the hub's cards.

```csharp
review.OpenPlan(new SetupPlan { Title, Summary, Steps = [..], RestartsGateway, Warnings }, onFinished);   // N invocations, reviewed together, run in order
NotificationRouting.Diff(before, after) / .Argvs(changes, restartAfter)   // N x ["setup","notifications-set", slot, on|off] - only the last restarts

ConnectorBatch.Argv(connectors, extra, mode, restart)    // ["setup","--yes","--connector",X,..,"--detected"|"--all","--mode",M,"--no-restart"]
SetupStateLines.Guardrail(config) / .Connector(config, target) / ...      // CardState(Text, Detail), config.yaml only; nothing runs
```

- **The runner is `DiscoverActionReview`, not a second one.** A plan is its `Steps` (it always had a list): every step in order, the next only when the one before exited 0, each through `CliRunner` (so each is its own Activity entry), the installation guard and `CatalogTrust` asked again at Confirm. What was added is the report: `DiscoverStepOutcome` per step (Succeeded, Failed, NotRun) and `PlanReport.Describe` - "1 of 3 steps succeeded. Step 2 failed (exit 1). Step 3 was not run. The steps that succeeded are not undone." - which the review's result line carries for a multi-step run (a single step's text is unchanged). `WizardViewModel` and `WizardDefinition` were deliberately not given a `FollowUps` list: the three flows are forms of their own with a form's own validation, and the wizard files are being edited by other work.
- **Notification routing** (Setup hub: the *Notifications* and *Notification categories* tiles open it). Six switches in the TUI's order and words, seeded from config.yaml with the runtime's defaults for a key it does not name (`ConfigYamlReader`: a read-only path reader that takes `yes/no/on/off` as PyYAML does, and never throws). **Only the switches that moved are sent**; none moved is "Nothing to apply" and the button is off. Two moved are one review with two numbered steps.
